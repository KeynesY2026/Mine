# 无敌 AI 锦标赛评估与策略优化设计

**状态：** 设计草案，等待用户审阅  
**日期：** 2026-10-06

## 1. 目标

构建可复现的整局 AI 对战基准，并以实证驱动无敌 AI 的策略优化。目标是在标准棋局中，无敌 AI 对简单 AI 的胜率至少为 **70%**，对中等 AI 的胜率至少为 **60%**；两项结果的统计证据均需显著高于 50%，避免把随机波动误认为策略优势。

这不是单纯的参数搜索任务。若对战数据表明瓶颈来自信息利用、风险选择、炸弹时机、回合价值或策略架构，应提出并验证策略层面的改进。最终结论应报告最佳已验证策略和证据，不宣称对所有可能策略的数学全局最优。

## 2. 棋局与对战范围

标准设置取自当前 `README.md` 与 `index.html`：棋盘 `15×15`、`53` 颗雷、每方 `1` 枚炸弹；无敌 AI 的增强炸弹选项开启，AI 炸弹不禁用。对手分别为配置 ID `heuristic`（简单）和 `global-probability`（中等）；无敌 AI 为 `constraint-probability`。

每个种子生成一张标准雷图，并对每个对手进行两场配对对局：无敌 AI 分别担任蓝方和红方，以消除蓝方先手偏差。比分、胜负和动作均按正式 `MineCore.Game` 规则执行。平局以半胜计入胜率（奇数雷规则下预期罕见，但指标定义仍需完整）。

## 3. 可复现对战工具

新增无依赖的 Node CLI `scripts/ai-tournament.js`，使用 Node 内置模块和 `vm` 加载正式核心、AI 规划器、决策守卫及三个 AI 插件。工具注入带种子的 `crypto.getRandomValues` 实现，使雷图生成和 AI 随机平局选择可复现；不改生产随机数实现，也不使用浏览器 UI 定时器。

每回合模拟器应遵循应用中的实际流程：从当前公开棋盘建立 view 和共享分析，调用当前 AI，经过决策守卫验证，再执行 `open`、坐标 `bomb` 或授权的增强 `bomb-auto`；自动轰炸失败时执行合法公开回退动作。无效动作、AI 抛错、非法引擎状态或超过安全回合上限均作为模拟器错误报告，不能静默记成正常对局或改用更弱 AI 继续。

AI 决策输入仅包含正式 view 和公开分析。插件不得获得隐藏雷图，也不得在动作前使用隐藏状态选择普通坐标着法。模拟器需忠实实现现有 `cfgEnhancedAI` 授权的 `Game.bombBest()` 引擎自动炸弹例外：引擎可在执行该动作时检查真实雷图，但不将雷图或目标扫描结果返回给插件。隐藏雷图还可在对局结束后用于评估决策结果及生成复盘材料。

CLI 至少支持：选择对手、种子范围/起始种子、每轮种子数、开发集或验证集、是否保存逐局轨迹，以及 JSON 汇总输出。每局 JSONL 轨迹应记录种子、座位、动作前公开状态、所选动作、动作结果、比分与最终赢家；隐藏雷图可另存于仅供赛后分析的字段或文件，不能被决策调用访问。默认输出简明汇总，便于人工和模型复盘。

新增 `test/ai-tournament.test.js`，验证同一对局种子与配置得到相同结果、种子成对换边使用相同初始雷图、双方 AI 的回合/炸弹动作遵守正式规则、隐藏雷图不在插件决策输入中，以及错误局不被计为有效样本。常规测试只跑小型烟雾/契约用例；完整锦标赛单独运行。

## 4. 统计协议与验收

对简单版和中等版分别计算无敌 AI 的胜率；胜局计 `1`、平局计 `0.5`、负局计 `0`。每个种子包含换边后的两场对局，报告游戏数、胜/平/负、点估计胜率、95% 置信区间、平均最终分差、炸弹使用率及无效/异常局数。

使用以种子为聚类单位的可复现 bootstrap 置信区间，避免将同一雷图的换边对局视作完全独立样本。使用不参与策略调优的独立验证种子确认候选策略。最终通过条件：验证集点估计分别达到 70% 和 60%，且每个 95% 置信区间下界均高于 50%。若结论仍不确定则增加样本；若未达到门槛须如实报告，不得把开发集成绩当作最终验证。

初始基线应先运行现有策略，不修改生产决策逻辑。基线后先在开发种子上形成可检验假设，每次只应用一项有明确原因的策略调整；每轮对两种对手回归，比较同一批成对开发种子上的差异。候选方案稳定后再运行独立验证集。固定种子不得成为唯一优化目标；必要时增加未使用的新种子集检验鲁棒性。

## 5. 复盘与模型分析

每轮复盘先由对战结果确定输局类别及重复模式，例如高风险开格、错过确定雷、炸弹过早/过晚、未利用连行动、局部收益与胜线规划不匹配。生成代表性完整对局轨迹与汇总统计，交由独立大模型只读分析，请其给出根因、可能的策略改进及可证伪预测。模型分析不直接写代码、不被视为事实；每个建议必须先在真实规则下形成实验假设，再以开发种子和独立验证种子检验。

若失败集中于参数门槛，可以调策略参数；若根因涉及概率信息、回合规划或策略分层，则可提出更结构性的改进。首轮基线复盘应明确检验用户提出的炸弹策略方向：取消仅依赖固定落后分数的单一门槛，结合炸弹预期收益与追回比分的可能性；若最后一炸高概率能直接赢局，应允许其覆盖常规出手限制。现有共享分析只暴露 `expectedMines`，并不等于“赢局概率”；若候选方案需要概率判断，必须先定义并验证可由公开信息计算的指标，或使用既有授权自动炸弹路径的安全边界，不得把期望值冒充成胜率。每轮保存策略版本、变更动机、测试种子集、指标和结论，以便复现及回滚。

## 6. 风险与边界

- 运行时长可能较高：使用独立 CLI、按对手/种子批次运行，并先测小批次性能，再决定正式样本量。
- 模拟器若自行复制 UI 调度逻辑，可能与应用行为漂移：测试必须覆盖决策守卫、增强炸弹授权/回退等关键契约，并在每次对战相关代码变化后运行。
- 开发集过拟合：验证集不用于提出或选择策略；候选策略只能在最终验证阶段使用该集合。
- 模型可能从赛后隐藏图推断信息：仅用作赛后审查，不得改变决策输入，也不能把事后全知判断直接当成可实现策略。
- 随机化与分座位效应：统一带种子随机源，固定雷图生成协议，并对每个种子交换座位。

## 7. 验证计划

1. 新增 CLI 后用固定种子各跑一局，确认可复现、出错显式失败、胜负符合真实引擎。
2. 运行对简单和中等 AI 的小规模基线，检查换边与配对统计正确。
3. 用当前全部 `node --test test/*.test.js` 回归，确保生产游戏规则与插件行为未被模拟器引入的改动破坏。
4. 运行基线正式批次并复盘；按实验记录迭代候选策略。
5. 对最终候选运行未参与调参的验证种子，按第 4 节门槛判定是否达到目标，并报告未解决风险。
